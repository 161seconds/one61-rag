# @aqua-calendar/infra-redis

Infrastructure package for Redis in the Aqua Calendar monorepo.

Goals:

- Standardize Redis connection and injection patterns.
- Group Redis capabilities into clear modules (`bullmq`, `cache`, `pubsub`).
- Remove duplicated Redis setup logic across apps.

## Architecture Overview

This package exports four main areas:

- `redis`: core connection/provider layer.
- `bullmq`: queue infrastructure using `@nestjs/bullmq`.
- `cache`: cache abstraction with Redis + `superjson`.
- `pubsub`: publish/subscribe abstraction with Redis Pub/Sub.

Top-level export:

- `src/index.ts` re-exports `redis`, `bullmq`, `cache`, and `pubsub`.

## Core Redis Layer (`redis/ioredis`)

### IoRedisInstanceKey

Supported connection keys:

- `BULLMQ`
- `CACHE`
- `PUBSUB_PUBLISHER`
- `PUBSUB_SUBSCRIBER`

### Provider token convention

Tokens are generated by:

- `createIoRedisKey(instanceKey)` -> `IOREDIS_<INSTANCE_KEY>`

Examples:

- `IOREDIS_BULLMQ`
- `IOREDIS_CACHE`
- `IOREDIS_PUBSUB_PUBLISHER`

### IoRedisModule

`IoRedisModule.register({ instanceKeys })`:

- accepts a list of `instanceKeys`
- creates one Redis provider per key
- exports those providers for other modules

### Environment config dependency

Providers read configuration from `@aqua-calendar/env` (`envConfig()`):

- `redis.bullmq.*`
- `redis.cache.*`
- `redis.pubsub.*`

Env loading behavior comes from `@aqua-calendar/env`:
- in `development`, env files are resolved from monorepo root (`<workspace>/.env*`)
- in non-development environments, default relative `ConfigModule` behavior is used unless overridden

If required keys are missing, runtime initialization will fail.

## BullMQ Module (`bullmq`)

### Purpose

Queue infrastructure for reminder jobs.

### Main components

- `BullQueueName.REMINDER_QUEUE`
- `ReminderQueuePayload`
- `BullMQModule.forRoot(...)`
- `BullMQModule.registerQueue(...)`

### Behavior

`BullMQModule.forRoot(...)`:

- creates the `BULLMQ` Redis connection through `IoRedisModule`
- configures `NestBullModule.forRootAsync(...)` with that injected connection
- auto-registers all queues listed in `BullQueueName`

Default job options:

- `removeOnComplete: true`
- `removeOnFail: true`
- `attempts` and `backoff.delay` from BullMQ env config

## Cache Module (`cache`)

### Purpose

A typed cache wrapper with `superjson` serialization.

### Main components

- `CacheModule.forRoot(...)`
- `CacheService`
- `InjectRedisCache()`
- `cacheKey` (key-builder constants)

### Current `CacheService` API

- `set({ key, value, ttl })`
- `get(key)`
- `mget(keys)`
- `mset([{ key, value, ttl }])`
- `del(key)`
- `mdel(keys)`

### Important note for AI agents

Current implementation details to remember:

- `mget` uses `forEach(async ...)`, so reads are not awaited correctly.
- `mset` also uses `forEach(...)` without awaiting `set` calls.

For stronger consistency, prefer `Promise.all(...)` or `for...of` with `await`.

## Pub/Sub Module (`pubsub`)

### Purpose

Publish/subscribe abstraction over Redis channels (topics).

### Main components

- `PubSubModule.forRoot(...)`
- `PubSubService`
- `InjectRedisPubSubPublisher()`
- `InjectRedisPubSubSubscriber()`
- Types: `PublishParams`, `SubscribeParams`, `PubSubHandler`

### Behavior

`PubSubModule.forRoot(...)`:

- supports `mode`:
  - `"publisher"` -> registers only `PUBSUB_PUBLISHER`
  - `"subscriber"` -> registers only `PUBSUB_SUBSCRIBER`
  - `"both"` (default) -> registers both
- exports `PubSubService`

`PubSubService`:

- `publish({ channel, payload })` serializes with `superjson` and publishes
- `subscribe({ channel, handler })` registers a handler for a channel
- `unsubscribe(channel)` unsubscribes from a channel
- `onModuleDestroy()` unsubscribes all tracked channels in the current process
- throws explicit runtime errors if the module mode does not provide the required client (publisher/subscriber)

### Operational notes

- Redis Pub/Sub is best-effort and non-durable.
- If consumers are offline, messages can be lost.
- For critical and retryable workflows, use BullMQ.

## Quick Usage

### 1) Queue worker/app

```ts
imports: [
  BullMQModule.forRoot({ isGlobal: true }),
]
```

### 2) Cache

```ts
imports: [
  CacheModule.forRoot({ isGlobal: true }),
]
```

Inject:

```ts
constructor(private readonly cacheService: CacheService) {}
```

### 3) Pub/Sub publisher or subscriber

```ts
imports: [
  PubSubModule.forRoot({ isGlobal: true, mode: "both" }),
]
```

Publisher-only app:

```ts
imports: [
  PubSubModule.forRoot({ isGlobal: true, mode: "publisher" }),
]
```

Subscriber-only app:

```ts
imports: [
  PubSubModule.forRoot({ isGlobal: true, mode: "subscriber" }),
]
```

Inject:

```ts
constructor(private readonly pubSubService: PubSubService) {}
```

Publish:

```ts
await this.pubSubService.publish({
  channel: "notification:reminder:created:v1",
  payload: { reminderId: "..." },
})
```

Subscribe:

```ts
await this.pubSubService.subscribe({
  channel: "notification:reminder:created:v1",
  handler: async (payload) => {
    // handle payload
  },
})
```

## Suggested channel naming

Use a stable naming convention:

- `<domain>:<entity>:<event>:v<version>`
- Example: `notification:reminder:created:v1`

## Notes for AI agents

- Treat this as an infrastructure package only.
- Keep boundaries clear:
  - queue -> `bullmq`
  - cache -> `cache`
  - realtime events -> `pubsub`
- Do not add business/domain logic here.
- When adding a new Redis capability, follow this order:
  1. add a new `IoRedisInstanceKey`
  2. map env/config in `ioredis.providers.ts`
  3. create a dedicated module and export it from `src/index.ts`
